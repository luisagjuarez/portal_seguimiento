# Bitácora — 2026-08-27

## Fase 1.14 (extraoficial) — Publicar el portal bajo el subpath /dovela_control

Infraestructura pidió que el portal responda bajo un subpath fijo (`http://host:5173/dovela_control`)
en vez de en la raíz, de cara a ponerlo detrás de un dominio/reverse-proxy compartido —
confirmado con el usuario: la API también debe quedar accesible por el mismo host/puerto que el
frontend (no en su propio origen como hoy), y la raíz (`/`) debe seguir funcionando en paralelo
con la misma app. Plan completo en `/home/lg/.claude/plans/stateful-stirring-oasis.md`
(sobrescribió el plan de la Fase 1.13 en el mismo archivo, tarea distinta).

**Diseño**: el nginx del contenedor `frontend` pasa a ser el único punto de entrada — sirve la
SPA bajo `/dovela_control` (y también en `/`, mismo build) y hace de reverse proxy de
`/dovela_control/api/*` hacia el contenedor `api` interno (`http://api:8000/api/`, ya resoluble
por DNS de compose). El navegador termina viendo un solo origen, sin CORS de por medio. El
puerto directo de la API (8000 local, 8005 TEST) se dejó publicado sin cambios, en paralelo.

**Hallazgos no obvios que cambiaron el diseño**:
- Vite reescribe *cualquier* URL raíz-absoluta de `index.html` (no solo los imports de `src/`)
  anteponiéndole `base` al compilar — incluye el `<script src="/config.js">` escrito a mano.
  Con `base: "/dovela_control/"` todo el bundle (JS, CSS, imágenes, `config.js`) queda pidiendo
  `/dovela_control/...` sin importar por qué URL se cargó la página. Por eso el build se copia
  entero a una subcarpeta real `dovela_control/` dentro de lo que sirve nginx, en vez de
  intentar reescribir rutas a mano.
- `frontend/src/api.js` arma las URLs como `` `${API_BASE_URL}/api/...` ``, y 3 funciones
  (`fetchClientes`, `fetchSolicitudes`, `fetchTareasTablero`) usan `new URL(...)` sin un
  segundo argumento de base — exige que `API_BASE_URL` siga siendo una URL absoluta (con
  esquema y host), nunca un path relativo. La solución no fue tocar `api.js`: se cambió el
  *valor* de `API_BASE_URL` para que ya incluya el subpath (`http://host:5173/dovela_control`)
  — cero cambios de código ahí.
- `FRONTEND_ORIGIN` se usaba para dos cosas con requisitos distintos: CORS (`allow_origins`,
  que por spec no puede llevar path) y el link de recuperación de contraseña. Se separaron:
  `FRONTEND_ORIGIN` queda intacto (solo origen), y se agregó `FRONTEND_BASE_PATH` (nuevo campo
  en `config.py`, default fijo `/dovela_control`) usado solo al armar el link de reset.
- nginx trae por default `client_max_body_size 1m`, que nunca aplicó porque el navegador le
  pegaba a la API en otro puerto, sin pasar por nginx. Al volverlo reverse proxy hacía falta
  subirlo (a 15 MB) o se rompía la carga de adjuntos (tope real de 10 MB en la app) — probado
  subiendo un adjunto de ~9 MB de punta a punta por el proxy nuevo, funcionó.
- **Bug propio durante la implementación, encontrado y corregido en la misma sesión**: al mover
  el build a la subcarpeta `dovela_control/`, la raíz (`/usr/share/nginx/html`) seguía
  existiendo como directorio real pero sin `index.html` propio (la imagen base de nginx trae
  uno, el "Welcome to nginx!", que hubo que borrar para que no tapara la SPA en `/`). Con
  `try_files $uri $uri/ /dovela_control/index.html;`, nginx daba por resuelto el intento
  `$uri/` al encontrar el directorio raíz (aunque estuviera vacío de índice) y devolvía 403 en
  vez de seguir probando el fallback — se quitó el `$uri/` de la lista
  (`try_files $uri /dovela_control/index.html;`), que resolvió tanto `/` como `/dovela_control`
  correctamente.

**Verificado end-to-end, local y TEST**: 134 tests de backend en verde (sin cambios de lógica
de negocio, no hicieron falta tests nuevos). Por `curl`: `/dovela_control/` y `/` devuelven el
mismo HTML, un asset real responde 200, `config.js` trae la URL de API correcta, el proxy a
`/dovela_control/api/health` funciona, el puerto directo de la API sigue vivo en paralelo, y una
ruta profunda de la SPA (F5) cae bien al `index.html`. En navegador: recuperación de contraseña
de punta a punta (el link del correo real ya apunta a `.../dovela_control/?reset_token=...`,
completado con `DOVELA_WA` y su contraseña restaurada al valor ya documentado), login,
navegación por el sidebar, F5 en una ruta profunda (`/dovela_control/solicitudes/7`, con sesión
persistida), y la raíz funcionando en paralelo con la misma sesión (mismo origen, mismo
`localStorage`). En TEST: mismo despliegue (`t_apex`,
`/u01/docker_containers/portal_seguimiento`) — se preservó con `git stash`/`pop` el cambio local
no versionado de ese servidor (remapeo de puerto de la API a 8005, necesario porque el 8000 del
host ya lo usa otra app ajena a este proyecto) y se actualizó `API_BASE_URL` en su `.env` (no
versionado) a `http://10.20.110.57:5173/dovela_control`. Confirmado con `curl` y un login real
con `DOVELA_WA` contra la API por el proxy nuevo.

### Seguimiento same día — fix de mixed content al publicarlo en un dominio HTTPS real

Infraestructura publicó el portal en `https://apps.stofactura.com/dovela_control/` (reverse
proxy externo, fuera de este repo, que reenvía a TEST) y el login falló con "NetworkError" +
bloqueo de "contenido activo mixto": `config.js` seguía trayendo grabado el valor armado para
TEST (`http://10.20.110.57:5173/dovela_control`, en HTTP) y el navegador lo bloqueó porque la
página ahora cargaba por HTTPS.

**Causa de fondo**: ningún valor fijo grabado en el build puede servir para los tres accesos a
la vez (`http://localhost:5173`, `http://10.20.110.57:5173`, y `https://apps.stofactura.com`).
Se reemplazó el mecanismo de `config.js`/`docker-entrypoint.sh` (pensado justo para variar ese
valor por ambiente sin recompilar, pero solo contemplaba orígenes fijos) por un cálculo en
runtime en `frontend/src/api.js`: `` `${window.location.origin}/dovela_control` `` — funciona
automáticamente para cualquier dominio/IP/protocolo porque el nginx del frontend siempre expone
la API bajo el mismo origen que la página (nunca hace falta CORS ni configurar nada por
ambiente). Limpieza asociada: se borraron `public/config.js` y `docker-entrypoint.sh` (el
`Dockerfile` vuelve al `ENTRYPOINT` default de la imagen `nginx:alpine`), y `API_BASE_URL` salió
de `docker-compose.yml` y de ambos `.env` (local y TEST, no versionados).

Verificado: rebuild local y en TEST, `curl` confirmando que `/dovela_control/` ya no referencia
`config.js`, login real por `curl` contra `http://localhost:5173`, `http://10.20.110.57:5173` y
`https://apps.stofactura.com` (los tres), y login completo en navegador real contra el dominio
público. Commit `90d51dc`.

## Fase 1.13 (extraoficial) — Reglas de permisos más finas por rol

Trabajado en modo plan; plan completo en `/home/lg/.claude/plans/stateful-stirring-oasis.md`.
Hasta hoy solo había 2 reglas de rol reales en todo el portal (crear tarea y gestión de
usuarios, ambas solo Scrum Master) — editar/borrar solicitudes, editar/borrar tareas, y
crear/editar/borrar hitos/comentarios/ítems "por hacer" estaban abiertos a cualquier usuario
logueado, Team incluido. Investigación previa vía agente Explore mapeó ese estado exacto antes
de diseñar el cambio.

**Reglas definidas con el usuario e implementadas:**
- Solicitudes y tareas: crear sigue abierto a todos (solicitudes, sin cambio — son los canales
  de ingesta; tareas ya era solo Scrum Master). Editar sigue abierto a todos los logueados.
  **Borrar pasa a ser exclusivo del Scrum Master**; el resto del equipo (incluido Product
  Owner) usa el nuevo estatus "Cancelado" en vez de borrar.
- Comentarios, hitos, ítems "Por hacer": crear sigue abierto a todos. **Editar y borrar pasan a
  ser solo del autor del registro, o del Scrum Master** (moderación).
- Enlaces de tarea quedaron fuera de alcance: no existe ningún endpoint de editar/borrar
  enlaces hoy (solo crear y listar), así que no había nada que restringir.

**Hallazgo que amplió el alcance**: el catálogo `estatus_tarea` no tenía un código `CANCELADO`
(a diferencia del catálogo `estatus` de solicitudes, que sí lo tenía) — sin él, el equipo no
tendría cómo cancelar una tarea en vez de borrarla. Se agregó vía
`backend/sql/010_cancelado_tarea.sql`, corrida contra la BD real. Efecto colateral corregido en
el mismo trabajo: `list_tareas_vencidas`, `list_tareas_por_vencer` y
`list_carga_por_responsable` (Monitor, Fase 1.12) filtraban `codigo_estatus_tarea <>
'COMPLETADO'` para definir "tarea activa" — sin ajustar, una tarea cancelada aparecería como
vencida o inflaría la carga de un responsable. Se cambiaron las tres a `NOT IN ('COMPLETADO',
'CANCELADO')`. `list_distribucion_estatus` no necesitó cambio (cuenta todos los estatus por
diseño).

**Backend**: nuevo helper `require_autor_o_scrum_master` en `app/auth/dependencies.py` (no es
un `Depends` de FastAPI, porque el `creado_por` a comparar solo se conoce tras leer el registro
de la BD). `borrar_solicitud`/`borrar_tarea` pasaron de `get_current_user` a
`require_scrum_master`. `actualizar_comentario`/`borrar_comentario` y
`actualizar_por_hacer`/`borrar_por_hacer` ahora leen el registro antes de mutar (antes no lo
hacían) para poder chequear autoría; `actualizar_hito_tarea`/`borrar_hito_tarea` ya leían el
hito antes, solo se agregó el chequeo.

**Frontend**: único hueco real de props de rol en todo el frontend — `TareaDetallePage` no
recibía `usuarioActual`/`esScrumMaster` desde `App.jsx` (a diferencia de `SolicitudDetallePage`,
que sí). Se corrigió pasándoselos por la ruta `/tareas/:id`, y ahí se calcula
`esAutor(registro) = esScrumMaster || registro.creado_por === usuarioActual.usuario`, usado
para mostrar/ocultar Editar/Borrar de hito, comentario y "por hacer" (mismo patrón opcional
`{onEditar && (...)}` que ya usaba `ComentarioItem`, extendido ahora a `PorHacerItem`). El
checkbox de completado de "por hacer" (que reutiliza el mismo `PUT`) también se deshabilita si
no es autor/Scrum Master, para no dejar que el usuario intente una acción que el backend va a
rechazar con 403. `TareaItem.jsx` (lista de tareas dentro de una solicitud) ahora oculta
"Borrar" si no se le pasa `onBorrar` (gateado por `esScrumMaster` desde
`SolicitudDetallePage`); "Borrar Solicitud" se gateó igual.

**Consecuencia directa de la regla, anotada para que no sea sorpresa**: el toggle rápido de
completado de un ítem "por hacer" ahora solo lo puede marcar/desmarcar su autor o el Scrum
Master — antes cualquier usuario logueado podía tildar el ítem de cualquier otro.

**Tests**: 11 tests nuevos (`test_api_solicitudes.py`, `test_api_tareas.py` — incluye
casos de hito 403/200-autor-no-SM —, `test_api_comentarios.py`, `test_api_tarea_por_hacer.py`),
134 tests de backend en verde (123 + 11). No se agregó un test unitario para la exclusión de
`CANCELADO` en las queries del Monitor: el patrón de testing de este repo mockea
`repository.py` por completo a nivel de rutas (no existe ningún test que ejercite el SQL real
de `repository.py` directamente), así que un test "unitario" ahí no habría probado nada real —
se verificó en su lugar contra la BD real (ver abajo).

**Verificado**: `npm run build` en verde; se reconstruyeron y relevantaron los contenedores
`api`/`backend`/`frontend` (las imágenes no montan el código como volumen, había que
reconstruir para tomar los cambios). Verificación exhaustiva contra la API real con los 3
tokens de prueba (`DOVELA_LG` Scrum Master, `DOVELA_WA` Team, `DOVELA_JC` Product Owner): ciclo
completo de crear solicitud/tarea/comentario/hito/ítem "por hacer", con cada combinación
autor/no-autor/Scrum Master para editar y borrar (todos los 403/200/204 esperados,
confirmados). Se marcó una tarea de prueba como `CANCELADO` con `fecha_fin` en el pasado y se
confirmó que el Monitor real **no** la cuenta en "vencidas" ni en "carga por responsable" pero
sí en "distribución por estatus". Verificación visual en navegador (Chrome) logueado como
`DOVELA_WA` (Team): "Borrar Solicitud" oculto pero "Editar Solicitud" visible; el Tablero ya
muestra la columna "Cancelado" nueva (poblada dinámicamente desde el catálogo, sin cambio de
código en `TableroColumna.jsx`). Datos de prueba (solicitud id=68, tarea id=71, y sus
comentario/hito/ítem asociados) borrados físicamente al terminar.
